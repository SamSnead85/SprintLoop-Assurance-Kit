# Decision 0003: gate the v0.3 developer-utility prerelease

- Status: proposed; implementation under review
- Date: 2026-08-27
- Decision owner: unassigned until release approval
- Public design/threat review: https://github.com/SamSnead85/SprintLoop-Assurance-Kit/issues/4

## Context

The v0.1 and v0.2 lines established deterministic exact-candidate evaluation, an external protected-provider boundary, an offline-verifiable dossier, hardened Git observation, a composite Action, a no-secret shadow lane, and a six-tool local read-only MCP surface.

The next adoption risk is not another model or dashboard. An engineer needs a truthful path from a real checkout and ordinary CI artifacts to the existing assurance boundary without inventing custom glue or granting an agent release authority. That path must diagnose receiver setup, bind common evidence bytes, expose deterministic inspection where engineers work, and preserve the independently governed provider/verifier/authority chain.

## Proposed design decision

Prepare v0.3.0 as a GitHub-only prerelease with the following developer-utility surface:

1. An offline, read-only `doctor` command and library API establish supported runtime, Git `>=2.45`, exact tracked `HEAD` and tree, byte-exact protected policy/trust documents, receiver-controlled canonical expectations, and optional MCP configuration readiness. A warning is not enforcement readiness, and a passing doctor is not an assurance decision.
2. A dependency-free evidence collector safely reads JUnit, SARIF 2.1, SPDX 2.2/2.3/3.0.1, CycloneDX 1.4–1.7, in-toto/SLSA, and Sigstore artifacts. It returns exact raw-byte digests plus bounded privacy-minimized structural metadata under a versioned contract. Every item remains `claimsVerified: false`.
3. Collection output separates the host `root` used for safe acquisition from portable `pathBase` metadata used at bundle handoff. Evidence entry paths remain relative to `pathBase`; downstream manifest assembly composes them exactly once. Host paths never enter the portable record.
4. The local stdio MCP catalog grows additively from six to seven tools with `assurance_collect_evidence`. It operates only below a receiver-configured `bundle` grant, removes per-format summaries and evidence bodies from model-facing output, and remains `ADVISORY_READ_ONLY` and `enforcementEligible: false`.
5. CLI identity and parsing become explicit: `version`, canonical long flags, `--version` / `-V`, successful standard help, duplicate/non-canonical/positional rejection, and stable exit behavior. Values supplied with `=` preserve all bytes after the first separator.
6. Strict duplicate-key JSON handling, safer canonical object construction, root/document identity rebinding, aggregate bounds, fail-closed XML parsing, Git lazy-fetch prevention, and broader sensitive-material scanning become part of the reviewed v0.3 threat boundary.

The package remains `private:true`, MIT-licensed, zero-runtime-dependency, and distributed through GitHub source, Action, and checksum-addressed release assets only. No npm publication is authorized.

## Protected-provider invariants

This proposal does not change complete-provider eligibility:

- the manifest, evidence, verifier receipt, and authorization are materialized after and outside the exact candidate;
- receiver policy, trust roots, expected repository/environment, and current Git observations are protected from candidate control;
- receipt and authorization signatures are verified against receiver-owned public-key roles with principal, owner, and control-domain separation;
- authorization remains named, scoped, finite, and revocable;
- a complete result becomes a required check or deployment condition only through receiver-governed SCM/deployment controls; and
- an MCP result, collector output, doctor result, demo `PASS`, green shadow job, or candidate-produced artifact cannot create enforcement eligibility.

The Kit still does not operate identity, key management, authenticated provider retrieval, transparency anchoring, retention, SCM reconciliation, deployment effects, or compliance certification.

## Compatibility and migration record

This is a pre-1.0 minor release proposal. The following changes must be called out to adopters:

- v0.3 supports maintained Node 22 and 24 LTS lines only (`>=22.23.2 <23` or `>=24.20.0 <25`). Node 20 and odd-numbered release lines are EOL and fail closed rather than receiving a misleading compatibility claim.
- Git-backed observation requires Git 2.45 or newer so `--no-lazy-fetch` can fail closed. Older Git must fail before repository objects are inspected rather than silently weakening observation.
- CLI calls that relied on duplicate flags, positional arguments, uppercase or underscore option aliases, or values attached to presence-only booleans become usage errors. Automation must use the documented canonical flags.
- MCP clients that assume exactly six tools must tolerate or explicitly approve the additive seventh tool. Existing six tool names retain their advisory semantics.
- `assurance.sprintloop.dev/doctor-result/v1` and `assurance.sprintloop.dev/evidence-collection/v1` are new contracts. The latter requires `pathBase`; it must not be confused with an absolute filesystem root or copied as an evidence-item field into the current manifest schema.
- Collector `STRUCTURE_FULL` describes supported structural inspection, not claim verification or dossier `FULL`. `ENVELOPE_ONLY` does not authenticate a provenance or signature envelope.

No existing v0.2 tag, artifact, source revision, or Action revision is mutated by this work.

## Threat and privacy record

Release review must verify, rather than infer from documentation, that:

- strict JSON rejects duplicate keys, invalid UTF-8, unsafe Unicode, excessive depth/size, and ambiguous structure across CLI, doctor, collector, and MCP framing;
- canonicalization preserves ordinary own keys including names such as `__proto__` without prototype mutation or key loss;
- evidence acquisition rejects traversal, symlinks, non-regular files, hard-link aliases, root replacement, leaf replacement, mutation during read, per-file limits, aggregate limits, and format ambiguity;
- JUnit parsing rejects DTD/entity input and malformed XML; JSON formats apply bounded profile-specific structural validation;
- collector output excludes report messages, names, source locations, package/service names, vulnerabilities, subjects, builder identities, certificates, signatures, log bodies, and payloads;
- MCP grants reveal logical IDs/kinds rather than host paths, and model-facing evidence output excludes raw bytes and per-format summaries;
- doctor-owned Git invocations use argument arrays, allowlisted environment, fail-closed lazy-fetch disabling, no replacement objects, no prompts or credentials, and controlled errors; and
- MCP's loaded module graph adds no network, credentials, filesystem writes, source-control effects, private-key ingestion, signing, or model sampling.

These controls reduce user-space race and disclosure risk; they do not turn a candidate-writable filesystem into a receiver-owned boundary. Collection belongs after immutable artifact handoff in an isolated receiver phase.

## Publication gates

This proposal becomes an approved release decision only after all of the following are recorded against clean complete revisions:

1. Positive and adversarial doctor, collector, CLI, MCP, canonicalization, sensitive-data, Git-hostility, fixture, materializer, shadow-provider, Action, and installed-package tests pass across the supported Node range and declared operating-system matrix.
2. Treat the repository scanner as a configured pattern gate, not proof that no secret exists: re-verify GitHub secret scanning and push protection, review the v0.3 commit range/history, and keep private vulnerability reporting enabled before publication.
3. Machine output validates against the new source schemas, MCP `tools/list` matches actual input/output behavior, and documentation examples pass from the packed artifact.
4. `npm run verify` and a clean `npm run release:dry-run` pass; the generated package inventory, SPDX SBOM, package release record, notes, tarball, and `SHA256SUMS` agree exactly.
5. A reviewed Action/runtime revision is fixed before copyable examples and remote smoke workflows are pinned. All executable Action references use that complete immutable revision.
6. A separate clean release/tag source revision records final pins and release metadata. Its identity, artifact digests, and relationship to the reviewed Action/runtime revision are explicit.
7. The doctor and evidence-collection schemas are served from their advertised HTTPS identifiers with the correct media type and exact reviewed bytes.
8. Hosted CI, golden path, remote immutable Action smoke, release-candidate dry-run, branch/security settings, private vulnerability reporting, and protected tag behavior pass.
9. README, changelog, roadmap, MCP guide, collector guide, doctor guide, source inventory, support path, maintainer ownership, and commercial boundary agree with actual behavior and pre-1.0 limits.
10. At least one clean-room evaluator reproduces the checksum-first demo and one controlled own-repository pilot records diagnostic utility without reporting a false `PASS`.

## Commercial and community boundary

The MIT Kit remains the portable protocol and adoption layer. A commercial SprintLoop service may add operated identity, tenant isolation, policy administration, key lifecycle, authenticated exact-coordinate retrieval, evidence retention, required-check reconciliation, SIEM/audit export, support, and governed pilots without making the public evaluator proprietary or model-dependent.

Release promotion must disclose project affiliation, follow each community's rules, and lead with a reproducible technical result and limitations. Purchased stars, automated engagement, star exchanges, sockpuppets, synthetic field reports, undisclosed promotion, and claims of customer proof without evidence are outside project policy.

## Current decision

Do not tag, publish, announce v0.3 as released, update copyable integrations to an invented revision, publish to npm, enable enforcement, or claim production/compliance readiness under this proposed record. A release owner must replace the status, owner, immutable revisions, gate evidence, and final authorization in a reviewed follow-up commit.
