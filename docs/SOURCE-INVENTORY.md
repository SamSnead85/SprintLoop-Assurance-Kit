# Source inventory and provenance boundary

This inventory defines what may enter the public SprintLoop Assurance Kit repository.

## Authored source

All JavaScript under `src/`, `bin/`, `scripts/`, and `test/`; all JSON Schemas under `schemas/`; the evaluator, bundle-materializer, and advisory shadow-provider composite Actions and workflows; examples; decision semantics; provider contract; threat model; integration guidance; and governance documents were authored specifically for this public kit.

The implementation is a clean, dependency-free Node.js design. The model-facing MCP process loads an isolated module graph—not the general signing/write-capable CLI—using dedicated read-only JSON and public-key verification modules. No private assurance engine, private service implementation, customer adapter, private repository history, customer configuration, internal operational data, or unresolved-provenance source is copied into this tree.

## Design inputs

The kit uses public, non-code conventions and platform interfaces:

- Git commit and tree object identifiers
- SHA-256 and Ed25519 through the Node.js standard library
- [XML 1.0](https://www.w3.org/TR/xml/) well-formedness conventions and the de facto JUnit `testsuite` / `testsuites` report envelopes emitted by pytest and Node.js
- [SARIF 2.1.0](https://docs.oasis-open.org/sarif/sarif/v2.1.0/sarif-v2.1.0.html)
- [SPDX 2.2](https://spdx.github.io/spdx-spec/v2.2.2/) and [2.3](https://spdx.github.io/spdx-spec/v2.3/) JSON document structures, plus the [SPDX 3.0.1 JSON-LD serialization](https://spdx.github.io/spdx-spec/v3.0.1/serializations/)
- [CycloneDX 1.4 through 1.7](https://cyclonedx.org/specification/overview/) JSON document structures
- [in-toto Statement v0.1/v1](https://github.com/in-toto/attestation/tree/main/spec) and [SLSA provenance v0.2/v1](https://slsa.dev/spec/v1.0/provenance) envelopes
- [Sigstore bundle v0.1 through v0.3](https://github.com/sigstore/protobuf-specs/blob/main/protos/sigstore_bundle.proto), including the bounded JSONL transport emitted by GitHub CLI artifact-attestation downloads
- JSON Schema draft 2020-12 vocabulary
- GitHub composite Action and workflow syntax
- Model Context Protocol `2026-07-28`, `2025-11-25`, and `2025-06-18` public JSON-RPC/stdio interface conventions
- JSON Schema draft 2020-12 tool input/output contracts
- The standard MIT license text

These inputs inform interoperability; they do not contribute copied third-party source code. The only workflow dependency is `actions/checkout`, referenced by an immutable reviewed commit.

## Generated fixtures

`scripts/generate-fixtures.mjs` creates the signed conformance bundles directly under `fixtures/`. It generates Ed25519 keys ephemerally, writes public keys and signed fictional documents, and never writes a private key. The repositories, principals, owners, environments, evidence, and identifiers created by that generator are synthetic.

Changing a fixture generator changes signatures because keys are generated afresh. Fixture semantics—not signature bytes—are the stable conformance contract.

## Real-producer interoperability corpus

`fixtures/collector-producers/` is a separate, source-only compatibility corpus; it is not generated by `scripts/generate-fixtures.mjs` and is not synthetic in the same sense. It contains public-safe outputs from pytest 9.0.2, GitHub CodeQL, Syft 1.31.0, a public `cli/cli` GitHub artifact attestation, and Cosign 3.1.3. Its [corpus inventory](../fixtures/collector-producers/README.md) records immutable source revisions or release checksums, exact transformations, fixture digests, reproduction commands, and license treatment for each file.

The copied CodeQL SARIF retains its upstream MIT notice. SPDX output declares CC0-1.0 data licensing; Syft and Cosign are Apache-2.0. The GitHub attestation is public workflow data. The Cosign fixture was verified before its ephemeral private key was deleted; only its public key remains. No third-party source code, remote schema, private key, account credential, customer data, or person-identifying certificate subject is included.

The corpus proves that the local structural collector can consume representative producer output. It does not authenticate the reports, establish their truth or completeness, verify the checked-in signatures during normal tests, or grant release authority. Volatile values were either left byte-exact or normalized only as documented in the corpus inventory; no malformed structure was repaired. Corpus files and tests intentionally remain in the GitHub source tree rather than the npm-format installation artifact, which contains runtime, schemas, Actions, and operator documentation only.

## Generated release artifacts

`artifacts/` is ignored source output. It may contain a demo dossier, SPDX SBOM, npm-format installation tarball used only for local smoke testing, package release record, release notes, and `SHA256SUMS`. These files are not authored source and are regenerated from a clean reviewed commit.

The npm-format tarball is a test and GitHub prerelease artifact. `package.json` is `private:true`; no npm publication is authorized.

## Dependency and data boundary

- Runtime dependencies: zero
- Development package dependencies: zero
- Customer or production data: prohibited
- Credentials or private keys: prohibited
- Personal names or personal contact details: prohibited
- Private repository links or internal filesystem paths: prohibited

The release gate requires this inventory, a clean full Git revision, tests, adversarial fixtures, sensitive-data scanning, SBOM generation, package installation smoke, and a deterministic package release record before it can create a release candidate.
